# Sandbox options for Ingenius / SkillOpt replay

Research date: 2026-09-26. Sources are limited to the projects' official GitHub repositories and repository-hosted documentation.

> **Status:** Research recommendation only. No sandbox below has been installed, configured, containment-tested, or validated with the Codex/SkillOpt replay workflow.

## Recommendation

Pilot **Microsandbox as the leading local candidate**, provided the replay host supports its beta hardware-virtualization runtime: KVM on Linux, Apple Silicon on macOS, or Windows Hypervisor Platform on Windows. It is a strong match on paper because it combines hardware-isolated microVMs, OCI images and arbitrary CLI execution, local operation without a persistent control-plane service, snapshots and live branching, host-controlled network allow-lists, and secret substitution that keeps the real credential outside the guest. Adopt it only after the validation gates below pass.

Pilot **E2B Cloud as the managed fallback and CI overflow candidate**. E2B has Firecracker isolation, pre-booted snapshot templates, pause/snapshot/resume, parallel managed capacity, network policy, and egress-time credential injection. Its experimental AI SDK adapter documents a Codex bootstrap captured once and reused from a snapshot. **Vercel Sandbox is a credible managed alternative** if the surrounding runner is already on Vercel: it has Firecracker VMs, persistent named sandboxes, snapshot trees and forks, custom images, and granular documented network/credential-brokering controls.

Use **just-bash only as an optional tier-0 smoke-test backend** for pure shell parsing, file-routing, and fixture-transform tests. It is not a SkillOpt replay backend for the actual Codex CLI because it cannot execute arbitrary native binaries. Keep **Kubernetes Agent Sandbox + gVisor** as a later fleet-scale option, not the first implementation: it supplies strong ownership and scale controls but carries substantially more cluster, runtime, storage, and policy operations.

Do **not** adopt the public Daytona code for a new test harness. Its repository states that it has been unmaintained since June 2026 and that core development moved to a private codebase.

## Proposed replay design

1. **Pin the test inputs in Git.** Record the Ingenius repository commit, candidate skill-tree hash, `tasks.json` hash, runner version, model identifier/settings, sandbox image digest, and policy version for each batch. The sandbox repository supplies infrastructure; the Ingenius Git repository remains the system of record for tasks, manifests, results, and decisions.
2. **Build one minimal gold environment.** Start from a pinned OCI digest, install the exact Codex/SkillOpt/runtime dependencies, copy the evaluation fixture and read-only source snapshot into the guest, then create a Microsandbox snapshot. Do not mount the working Ingenius checkout read-write.
3. **Fork per `(candidate, task, repeat)`.** Each replay gets a fresh branch from the same gold snapshot and a private writable worktree. Run tasks concurrently up to an explicit CPU/RAM budget; never reuse a mutated sandbox between scored runs.
4. **Keep credentials outside the guest.** Default-deny egress; allow only the model endpoint required by the runner. Broker the model credential at the host/network boundary. Avoid giving the sandbox a GitHub write token; if source access is unavoidable, broker a read-only, repository-scoped token and restrict the destination hosts. Prefer preloading the exact Git commit so GitHub access is unnecessary during scoring.
5. **Return structured evidence through a trusted controller.** Capture prompt/task ID, stdout/stderr, exit status, timing, token/usage metadata when available, produced answer, scorer result, and file diffs. The host controller validates paths and writes immutable result artifacts under the evaluation directory; the guest does not commit or push.
6. **Test containment before trusting scores.** Add negative canaries that attempt host-file reads, unexpected writes, metadata/RFC1918 access, unapproved outbound hosts, and secret printing. A backend is accepted only when those attempts fail and normal model traffic still succeeds.
7. **Use two execution tiers.** Run cheap deterministic harness/unit checks in just-bash or the host test process, then run every behaviorally scored Codex replay in a real microVM. Periodically replay a small fixed canary set on E2B or Vercel to detect local-runtime-specific behavior.

## Decision gates

Before adopting any backend, run a live spike that proves the exact Codex CLI version and installation path, native skill discovery, noninteractive brokered authentication, model-endpoint allowlisting, clean snapshot/fork state, absence of host read-write exposure, and two to four concurrent replay runs.

- Pilot **Microsandbox first** if the available host can run its hardware virtualization backend and the secret/network interception path works with the model client.
- Pilot **E2B Cloud** if host virtualization is unavailable, managed fan-out matters more than local custody, or the experimental Codex bootstrap adapter saves material integration work.
- Pilot **Vercel Sandbox** instead of E2B when Vercel project/OIDC integration already exists or its persistent fork/network-policy API is the better organizational fit.
- Revisit **Agent Sandbox + gVisor/Kata** only when there is a sustained need for a shared multi-node replay service, warm pools, tenancy, quotas, or hundreds-to-thousands of concurrent runs.

## Primary-source notes

- E2B's architecture describes each sandbox as a Firecracker process in its own cgroup and network namespace and creation as restoration of pre-booted snapshots: [architecture](https://github.com/e2b-dev/runtime/blob/main/docs/ARCHITECTURE.md).
- Vercel's repository describes Sandbox as an isolated Firecracker Linux VM; its repository-hosted [Sandbox skill reference](https://github.com/vercel/sandbox/blob/main/skills/sandbox/SKILL.md) documents persistence, forks, snapshots, custom images, network policies, and credential transformations.
- Kubernetes Agent Sandbox explicitly describes itself as an orchestrator that delegates low-level isolation to runtime classes; its [threat model](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/docs/security/threat_model.md) documents the managed NetworkPolicy and service-account-token defaults, while its [configuration guide](https://github.com/kubernetes-sigs/agent-sandbox/blob/main/docs/configuration.md) documents controller concurrency.
- gVisor's [security introduction](https://github.com/google/gvisor/blob/master/g3doc/architecture_guide/intro_to_gvisor.md) explains the userspace-kernel boundary and rootless/no-network mode; its [security model](https://github.com/google/gvisor/blob/master/g3doc/architecture_guide/security.md) states that resource and network controls remain external.
- just-bash's [threat model](https://github.com/vercel-labs/just-bash/blob/main/THREAT_MODEL.md) is explicit about its in-process trust boundary and disabled-by-default network.
